Build a complete, polished, production-style intelligent public bus application for Chennai Metropolitan Transport Corporation (MTC).

PROJECT NAME:
MTC SmartBus — Intelligent Bus Tracking, Occupancy Forecasting & Passenger Information System

IMPORTANT:
This is NOT just a generic bus tracking application.

The core differentiating feature is:

"Show the passenger the current physical occupancy of an MTC bus and dynamically predict approximately how many passengers will be inside that bus when it reaches the passenger's selected physical bus stop."

The system combines:
1. Existing MTC CCTV passenger movement data
2. ETM transaction information
3. GPS / live bus location
4. Edge-AI occupancy processing
5. Occupancy reconciliation
6. Physical-stop-specific occupancy forecasting
7. Passenger-facing live information
8. Operator/fleet monitoring
9. Independent CCTV-based suspicious activity detection

The UI must be simple for normal passengers while exposing advanced analytics only to authorized operators/admins.

==================================================
1. PRODUCT VISION
==================================================

The application should answer four main passenger questions:

1. Where is my bus?
2. When will my bus reach my stop?
3. How crowded is my bus right now?
4. How crowded is my bus expected to be when it reaches MY stop?

The main passenger experience should therefore be:

CURRENT LOCATION
        ↓
SELECT BUS
        ↓
SELECT BOARDING / TARGET PHYSICAL STOP
        ↓
VIEW LIVE BUS LOCATION
        ↓
VIEW CURRENT OCCUPANCY
        ↓
VIEW PREDICTED OCCUPANCY AT TARGET STOP
        ↓
VIEW APPROXIMATE CROWDING LEVEL

The prediction must be dynamic and update as new passenger movement, ETM and GPS information becomes available.

Do NOT make the prediction a fixed value.

==================================================

MTC routes have ordered stages/stops and route information includes:

- Route

- Physical Stop
- Bus

9. CORE OCCUPANCY FEATURE
==================================================

This is the most important feature of the entire application.

The application must maintain two major passenger-count information sources:

A. LIVE CAMERA OCCUPANCY

Derived from passenger movement observed by the onboard MTC CCTV cameras.

B. ETM DESTINATION INFORMATION

Derived from available ETM transactions.

The application should never pretend that ETM transactions are instantaneous.

ETM transactions may arrive progressively/delayed.

Therefore maintain separate timelines.

CAMERA TIMELINE:
Immediate / continuous

ETM TIMELINE:
Delayed / progressive

==================================================
10. LIVE CAMERA OCCUPANCY
==================================================

Use the following conceptual model:

C(t) = C(t-1) + I(t) - O(t)

Where:

C(t) = current occupancy
I(t) = passengers entering
O(t) = passengers exiting

The backend should expose:

currentOccupancy
entriesRecent
exitsRecent
occupancyTimestamp
occupancyConfidence
occupancySource

Example:

Current occupancy:
32

+4

-2

Last update:
8 seconds ago

==================================================
11. OCCUPANCY RECONCILIATION
==================================================

Create a backend/service layer called:

Occupancy Reconciliation Engine

At defined checkpoints, use available ETM information to establish a reconciled occupancy reference.

Conceptual methodology:

Previous Reliable Occupancy
+
ETM Recorded Passenger Entries
-
Destination-Based Expected Alighting
=
Reconciled Occupancy Reference

The reconciled reference should then synchronize the live camera occupancy.

After synchronization:

CONTINUE LIVE CAMERA COUNTING

Do NOT display this mathematical mechanism to ordinary passengers.

This is an internal system feature.

Authorized operators can see it.

==================================================
12. PHYSICAL-STOP OCCUPANCY FORECAST
==================================================

Create:

Physical Stop Occupancy Forecast Engine

Inputs:

1. Latest / reconciled occupancy
2. Current passenger-flow information
3. ETM destination-based expected alighting
4. GPS / physical route position
5. Ordered upcoming physical stops

Conceptual model:

Latest Occupancy State
+
Current Passenger-Flow Information
-
Destination-Based Expected Alighting
=
Predicted Occupancy

Output:

Predicted Occupancy at Target Physical Stop

IMPORTANT:

Do NOT use:
"Expected future boarding passengers"

as a fixed value.

The prediction must dynamically update from the current passenger-flow state.
